## 三、技术短板深度分析与补充方案

### 3.1 短板一：实时通知（WebSocket）— 优先级：高

**问题分析**：
运维工单系统需要实时推送以下场景的通知：
- 新工单创建时通知处理人
- 工单状态变更时通知相关人员
- 工单超时预警提醒
- 工单评论/沟通消息推送

**补充方案**：集成Spring WebSocket

| 方案 | 技术选型 | 复杂度 | 推荐度 |
|------|----------|--------|--------|
| 方案A | Spring WebSocket + STOMP | 中 | ★★★★★ |
| 方案B | SSE (Server-Sent Events) | 低 | ★★★★☆ |
| 方案C | 第三方推送（极光/个推） | 低 | ★★☆☆☆ |

**推荐方案A**：Spring WebSocket + STOMP协议

```
技术栈补充：
- spring-boot-starter-websocket（Spring Boot 4.x内置）
- STOMP协议（基于SockJS降级兼容）
- 前端：@stomp/stompjs + sockjs-client

实现架构：
WebSocketConfig → WebSocketMessageBroker → 消息路由
  ├── /topic/ticket/{id}     工单详情实时更新
  ├── /user/queue/notify     个人通知队列
  └── /app/ticket/action     工单操作消息

集成方式：
1. 在ruoyi-framework模块添加WebSocketConfig配置类
2. 在ruoyi-common添加WebSocket工具类
3. 前端添加WebSocket连接管理Service
4. 与现有JWT认证集成（握手时验证Token）
```

### 3.2 短板二：工作流引擎 — 优先级：高

**问题分析**：
工单系统的核心是工单的流转，包括：
- 多级审批流程（提交→审核→分配→处理→验收→关闭）
- 条件分支（根据工单类型/优先级走不同流程）
- 会签/加签（多人审批）
- 驳回/退回（退回到指定节点）

**补充方案对比**：

| 方案 | 技术选型 | 复杂度 | 灵活性 | 推荐度 |
|------|----------|--------|--------|--------|
| 方案A | Flowable 7.x | 高 | ★★★★★ | ★★★★☆ |
| 方案B | 自研状态机 | 中 | ★★★☆☆ | ★★★★★ |
| 方案C | Spring StateMachine | 中 | ★★★★☆ | ★★★★☆ |

**推荐方案B**：自研轻量级状态机 + 数据库驱动

```
理由：
1. 毕业设计项目，Flowable过重（引入约200+张表），学习成本高
2. IT运维工单流程相对固定，不需要BPMN 2.0的完整规范
3. 自研方案更贴合业务需求，代码可控性强
4. 便于答辩时展示技术深度

技术设计：
- 数据库表：wf_workflow（流程定义）、wf_node（节点定义）、wf_transition（流转规则）
- 状态机核心：TicketStateMachine（枚举状态 + 事件驱动）
- 流转引擎：WorkflowEngine（解析流程定义 → 驱动状态转换）
- 前端可视化：基于Vue Flow（@vue-flow/core）的流程设计器

状态定义：
DRAFT(草稿) → SUBMITTED(已提交) → APPROVED(已审批) → ASSIGNED(已分配)
→ PROCESSING(处理中) → RESOLVED(已解决) → VERIFIED(已验证) → CLOSED(已关闭)
  ↓                                              ↑
REJECTED(已驳回) ─────────────────────────────────┘
```

### 3.3 短板三：消息队列 — 优先级：中

**问题分析**：
- 邮件/短信通知需要异步发送，避免阻塞主流程
- 工单统计报表生成耗时，需异步处理
- 工单超时检测需要延迟队列

**补充方案**：

| 方案 | 技术选型 | 复杂度 | 推荐度 |
|------|----------|--------|--------|
| 方案A | RabbitMQ | 中 | ★★★★☆ |
| 方案B | Redis Stream | 低 | ★★★★★ |
| 方案C | Spring Event（应用内事件） | 极低 | ★★★★☆ |

**推荐方案C + B组合**：
- 轻量场景使用Spring ApplicationEvent（应用内事件总线）
- 需要持久化/延迟队列时使用Redis Stream
- 避免引入额外中间件，降低部署复杂度

```
技术栈补充：
- Spring ApplicationEvent（已有基础）
- Redis Stream（利用现有Redis实例）

事件定义：
- TicketCreatedEvent      工单创建事件
- TicketAssignedEvent     工单分配事件
- TicketStatusChangedEvent 工单状态变更事件
- TicketSLAWarningEvent   SLA预警事件
- TicketCommentEvent      工单评论事件

事件处理链：
Event Publisher → ApplicationEvent → Async EventListener → [邮件/短信/WebSocket推送]
                                                         → [Redis Stream持久化]
                                                         → [操作日志记录]
```

### 3.4 短板四：全文搜索 — 优先级：中

**问题分析**：
- 工单标题/描述的模糊搜索（LIKE查询性能差）
- 工单内容的全文检索
- 搜索结果高亮显示

**补充方案**：

| 方案 | 技术选型 | 复杂度 | 推荐度 |
|------|----------|--------|--------|
| 方案A | Elasticsearch 8.x | 高 | ★★★☆☆ |
| 方案B | MySQL FULLTEXT索引 | 低 | ★★★★★ |
| 方案C | 数据库LIKE + 缓存优化 | 极低 | ★★★☆☆ |

**推荐方案B**：MySQL FULLTEXT索引

```
理由：
1. 数据量级（毕业设计）不需要Elasticsearch的分布式能力
2. MySQL 8.x的ngram全文解析器已支持中文分词
3. 无需额外部署中间件
4. 可通过RuoYi现有的MyBatis Plus直接使用

实现方式：
ALTER TABLE it_ticket ADD FULLTEXT INDEX ft_ticket_search(title, description) WITH PARSER ngram;

查询示例：
SELECT * FROM it_ticket WHERE MATCH(title, description) AGAINST('网络故障' IN NATURAL LANGUAGE MODE);

后续扩展：
如需更强大的搜索能力，可在二期引入Elasticsearch，通过Canal同步MySQL数据
```

### 3.6 短板六：数据变更追踪 — 优先级：低

- 工单修改需要记录详细的变更历史（谁在什么时间修改了什么字段）
- 需要支持工单变更对比查看

**补充方案**：

| 方案 | 技术选型 | 复杂度 | 推荐度 |
|------|----------|--------|--------|
| 方案A | 数据库触发器 | 低 | ★★☆☆☆ |
| 方案B | MyBatis Plus 乐观锁 + 变更记录表 | 中 | ★★★★★ |
| 方案C | Hibernate Envers | 高 | ★★☆☆☆ |

**推荐方案B**：自定义变更记录机制

```
技术设计：
- 变更记录表：it_ticket_change_log
```

## 五、技术风险评估

### 5.1 高风险项

| 风险项 | 风险描述 | 影响程度 | 应对策略 |
|--------|----------|----------|----------|
| Spring Boot 4.x稳定性 | 4.x为较新版本，生态兼容性可能存在隐患 | 高 | 充分测试，关注社区Issue |
| 自研工作流引擎 | 状态机设计不当可能导致流转死锁或遗漏 | 高 | 参考成熟方案，充分测试边界场景 |
| WebSocket集群部署 | 多实例部署时WebSocket会话管理复杂 | 中 | 使用Redis Pub/Sub做消息广播 |

### 5.2 中风险项

| 风险项 | 风险描述 | 影响程度 | 应对策略 |
|--------|----------|----------|----------|
| MySQL全文索引性能 | 大数据量下全文索引性能可能不足 | 中 | 控制索引字段数量，必要时引入ES |
| 邮件发送可靠性 | 邮件服务器可能被拒收或延迟 | 中 | 使用知名邮件服务商，增加重试机制 |
| 前端流程设计器 | Vue Flow组件学习曲线较陡 | 中 | 优先实现核心功能，可视化设计器可简化 |

### 5.3 低风险项

| 风险项 | 风险描述 | 影响程度 | 应对策略 |
|--------|----------|----------|----------|
| Redis Stream可靠性 | 消息丢失或重复消费 | 低 | 消费者组ACK机制，幂等处理 |
| 短信API稳定性 | 第三方短信服务可能不稳定 | 低 | 降级为仅邮件通知 |

## 七、结论与建议

### 7.1 总体结论

ITSM-Desk脚手架为IT运维工单管理系统提供了**坚实的技术基础**，其Spring Boot 4.x + MyBatis Plus + Vue 3的技术栈组合已覆盖约65%的核心需求。剩余35%的需求缺口主要集中在**实时通信、工作流引擎、消息队列和通知服务**四个维度，均可通过轻量级技术补充方案解决，无需引入重型中间件。

### 7.2 实施建议

1. **优先级排序**：WebSocket实时通知 → 自研工作流引擎 → 事件驱动通知 → 全文搜索 → 邮件/短信
2. **渐进式集成**：先使用Spring Event实现事件总线，验证业务逻辑后再考虑引入Redis Stream
3. **代码生成器利用**：充分利用RuoYi代码生成器快速搭建工单CRUD骨架，节省约40%的基础开发时间
4. **模块化设计**：工单核心模块（itsm-ticket）独立于系统模块，便于维护和扩展
5. **技术债务控制**：避免过度设计，毕业设计项目应以功能完整性和技术深度为优先

### 7.3 技术亮点规划

为使毕业设计区别于基础教学类项目，建议重点打造以下技术亮点：

| 亮点 | 技术深度 | 答辩展示价值 |
|------|----------|------------|
| 自研轻量级工作流引擎 | 状态机设计模式 + 数据库驱动 | ★★★★★ |
| WebSocket实时通知 | STOMP协议 + Redis消息广播 | ★★★★☆ |
| SLA服务等级协议引擎 | 定时检测 + 自动升级 | ★★★★★ |
| 工单统计仪表盘 | ECharts多维图表 + 实时数据 | ★★★★☆ |
| 事件驱动架构 | Spring Event + 异步处理 | ★★★★☆ |
| 数据变更追踪 | 反射对比 + 版本化存储 | ★★★☆☆ |
