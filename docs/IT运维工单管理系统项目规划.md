# 第一部分：项目需求分析

---

## 一、项目概述

### 1.1 项目背景

IT运维工单管理系统是IT服务管理（ITSM）的核心子系统，遵循ITIL（信息技术基础设施库）最佳实践框架，为组织提供标准化的IT服务请求管理、故障报告处理和问题跟踪能力。本系统作为毕业设计项目，需达到企业级Web应用标准，区别于基础教学类管理系统。

### 1.2 项目目标

| 目标维度 | 具体目标 |
|----------|----------|
| 功能完整性 | 覆盖工单全生命周期管理，包括创建、审批、分配、处理、验收、关闭 |
| 技术深度 | 体现工作流引擎、实时通信、事件驱动等企业级技术能力 |
| 用户体验 | 界面专业、操作便捷、响应迅速，符合运维工作场景 |
| 代码质量 | 遵循编码规范，具备完善的异常处理和日志记录 |
| 可扩展性 | 模块化设计，支持后续功能扩展和性能优化 |

### 1.3 用户角色定义

| 角色 | 职责 | 核心操作 |
|------|------|----------|
| **系统管理员** | 系统配置、用户管理、流程配置 | 用户/角色/权限管理、工作流配置、SLA配置 |
| **服务台人员** | 接收请求、工单分类、初步处理 | 创建工单、工单分类、指派处理人、工单跟踪 |
| **IT运维工程师** | 工单处理、故障修复 | 接收工单、处理工单、更新进度、提交解决方案 |
| **部门主管** | 审批、监督、绩效评估 | 工单审批、处理人分配、SLA监控、统计报表 |
| **普通用户** | 提交服务请求、查看进度 | 提交工单、查看状态、评价反馈、知识库查询 |

### 2.2 核心功能需求详述

#### 2.2.1 工单管理模块

**FR-TK-001 工单创建与提交**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 用户通过表单创建IT运维工单，填写故障描述、分类、优先级等信息 |
| 输入 | 工单标题、工单描述（富文本）、工单分类、子分类、优先级（紧急/高/中/低）、影响范围、附件 |
| 输出 | 工单编号（自动生成，格式：TK-YYYYMMDD-XXXX）、工单详情页 |
| 业务规则 | 1. 工单编号自动生成且唯一<br>2. 紧急工单需填写影响范围说明<br>3. 附件支持图片/文档/日志文件，单文件≤20MB<br>4. 提交后自动触发审批流程<br>5. 保存草稿功能 |

**FR-TK-002 工单审批与分配**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 主管或服务台人员对提交的工单进行审批，并分配给合适的处理人 |
| 输入 | 审批意见、处理人选择、预计完成时间 |
| 输出 | 审批记录、工单状态变更通知 |
| 业务规则 | 1. 审批通过后工单自动流转到"已分配"状态<br>2. 审批驳回需填写驳回原因，工单退回给提交人<br>3. 支持转派（重新分配给其他处理人）<br>4. 分配时自动通知处理人<br>5. 紧急工单跳过审批直接分配 |

**FR-TK-003 工单处理与跟踪**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 运维工程师接收工单后进行处理，记录处理过程和解决方案 |
| 输入 | 处理记录（富文本）、处理进度、工时记录、解决方案 |
| 输出 | 处理进度更新、状态变更通知 |
| 业务规则 | 1. 处理人可添加多条处理记录<br>2. 支持工时记录（开始/暂停/结束）<br>3. 处理过程中可请求协助（加签）<br>4. 提交解决方案后工单流转到"待验证"状态<br>5. 支持工单评论/沟通功能 |

**FR-TK-004 工单验收与关闭**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 提交人验证解决方案，确认问题是否解决 |
| 输入 | 验证结果（通过/不通过）、验证说明 |
| 输出 | 工单关闭/退回处理 |
| 业务规则 | 1. 验证通过后工单自动关闭<br>2. 验证不通过需填写原因，工单退回处理人<br>3. 关闭后自动发送满意度评价邀请<br>4. 超过7天未验证自动关闭 |

**FR-TK-005 工单评价与反馈**

| 属性 | 说明 |
|------|------|
| 优先级 | P1 - 应该 |
| 描述 | 工单关闭后，提交人对服务质量进行评价 |
| 输入 | 满意度评分（1-5星）、评价内容 |
| 输出 | 评价记录、满意度统计 |
| 业务规则 | 1. 评价为匿名，处理人不可见具体评价人<br>2. 评价后不可修改<br>3. 1-2星评价自动触发主管关注 |

#### 2.2.2 工作流引擎模块

**FR-WF-001 流程定义与管理**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 管理员定义工单流转流程，包括节点、条件和动作 |
| 输入 | 流程名称、流程描述、节点列表、流转条件 |
| 输出 | 流程定义配置、流程版本 |
| 业务规则 | 1. 支持多版本流程定义<br>2. 流程变更不影响进行中的工单<br>3. 默认流程：提交→审批→分配→处理→验证→关闭<br>4. 支持按工单分类关联不同流程 |

**FR-WF-002 流程可视化设计器**

| 属性 | 说明 |
|------|------|
| 优先级 | P2 - 可选 |
| 描述 | 提供可视化拖拽式流程设计器，直观配置工单流转流程 |
| 输入 | 拖拽操作、节点属性配置 |
| 输出 | 流程图、流程定义数据 |
| 业务规则 | 1. 基于Vue Flow实现<br>2. 支持节点拖拽、连线、属性编辑<br>3. 流程合法性校验（起始/终止节点、无死循环） |

#### 2.2.3 SLA管理模块

**FR-SLA-001 SLA等级定义**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 定义不同优先级工单的服务等级协议 |
| 输入 | SLA名称、优先级、响应时间、解决时间、升级规则 |
| 输出 | SLA配置 |

| 优先级 | 响应时间 | 解决时间 | 升级规则 |
|--------|----------|----------|----------|
| 紧急 | 15分钟 | 4小时 | 超时自动升级至部门主管 |
| 高 | 30分钟 | 8小时 | 超时自动升级至部门主管 |
| 中 | 2小时 | 24小时 | 超时自动提醒处理人 |
| 低 | 4小时 | 72小时 | 超时自动提醒处理人 |

**FR-SLA-002 SLA监控与预警**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 实时监控工单SLA执行情况，超时前预警 |
| 输入 | 工单创建时间、SLA规则 |
| 输出 | 预警通知、超时记录 |
| 业务规则 | 1. 响应时间剩余25%时发送预警<br>2. 解决时间剩余25%时发送预警<br>3. 超时后自动触发升级流程<br>4. SLA时间按工作时间计算（排除非工作时间） |

#### 2.2.4 通知中心模块

**FR-NTF-001 站内实时通知**

| 属性 | 说明 |
|------|------|
| 优先级 | P0 - 必须 |
| 描述 | 通过WebSocket实时推送工单相关通知 |
| 输入 | 事件触发（工单创建/分配/状态变更/评论/SLA预警） |
| 输出 | 浏览器通知弹窗、通知列表 |
| 业务规则 | 1. 基于WebSocket + STOMP实现<br>2. 支持通知已读/未读标记<br>3. 支持通知批量已读<br>4. 通知保留30天 |

**FR-NTF-002 邮件通知**

| 属性 | 说明 |
|------|------|
| 优先级 | P1 - 应该 |
| 描述 | 重要事件通过邮件通知相关人员 |
| 输入 | 事件触发、收件人、邮件模板 |
| 输出 | 邮件发送记录 |
| 业务规则 | 1. 工单分配/转派时邮件通知处理人<br>2. SLA超时预警时邮件通知<br>3. 工单关闭时邮件通知提交人<br>4. 邮件内容使用模板，包含工单详情链接 |

#### 2.2.5 知识库模块

**FR-KB-001 知识文章管理**

| 属性 | 说明 |
|------|------|
| 优先级 | P1 - 应该 |
| 描述 | 管理运维知识文章，沉淀解决方案 |
| 输入 | 文章标题、分类、标签、内容（富文本）、关联工单 |
| 输出 | 知识文章详情页 |
| 业务规则 | 1. 工单关闭时可一键生成知识文章<br>2. 文章支持审核发布流程<br>3. 支持点赞/收藏功能 |

**FR-KB-002 知识搜索**

| 属性 | 说明 |
|------|------|
| 优先级 | P1 - 应该 |
| 描述 | 全文搜索知识库文章 |
| 输入 | 搜索关键词 |
| 输出 | 搜索结果列表（含高亮） |
| 业务规则 | 1. 基于MySQL FULLTEXT索引实现<br>2. 支持中文分词搜索<br>3. 搜索结果按相关度排序 |

#### 2.2.6 统计分析模块

### 4.3 数据流向

#### 4.3.1 工单创建流程

```
用户提交工单
    │
    ▼
TicketController.createTicket()
    │
    ├── 参数校验（@Validated）
    ├── 权限校验（@PreAuthorize）
    │
    ▼
TicketService.createTicket()
    │
    ├── 生成工单编号（TK-YYYYMMDD-XXXX）
    ├── 设置初始状态（DRAFT/SUBMITTED）
    ├── 保存工单数据（MyBatis Plus → MySQL）
    ├── 保存附件信息
    │
    ├── 发布事件：TicketCreatedEvent
    │     ├── 通知服务：发送站内通知
    │     ├── 邮件服务：发送邮件通知
    │     └── SLA服务：启动SLA计时
    │
    └── 返回工单编号
```

#### 4.3.2 工单状态流转

```
TicketController.changeStatus()
    │
    ▼
WorkflowEngine.transition()
    │
    ├── 校验当前状态是否允许转换
    ├── 校验操作人权限
    ├── 执行前置动作（BeforeAction）
    │     ├── 记录变更日志
    │     └── 校验业务规则
    │
    ├── 更新工单状态
    │
    ├── 执行后置动作（AfterAction）
    │     ├── 发布事件：TicketStatusChangedEvent
    │     ├── SLA服务：更新SLA计时
    │     ├── 通知服务：推送状态变更通知
    │     └── 统计服务：更新统计数据
    │
    └── 返回操作结果
```

    │
    ▼
ApplicationEventPublisher.publishEvent()
    │
    ▼
@EventListener (异步)

    └── 短信发送（紧急工单）
          └── 阿里云短信API

### 5.3 数据库设计原则

1. **命名规范**：业务表前缀`it_`（ITSM），工作流表前缀`wf_`，遵循RuoYi现有`sys_`前缀规范
2. **审计字段**：所有表包含`create_by`、`create_time`、`update_by`、`update_time`
3. **逻辑删除**：核心业务表使用`del_flag`软删除
4. **索引策略**：高频查询字段建立索引，搜索字段建立全文索引
5. **字段类型**：金额/工时使用`decimal`，状态使用`varchar`（便于扩展），标志位使用`char(1)`
6. **大字段分离**：富文本内容使用`longtext`，与主表字段物理分离

## 附录A：工单状态机定义

```
状态枚举：
  DRAFT        草稿
  SUBMITTED    已提交
  APPROVED     已审批
  ASSIGNED     已分配
  PROCESSING   处理中
  RESOLVED     已解决
  VERIFIED     已验证
  CLOSED       已关闭
  REJECTED     已驳回
  CANCELLED    已取消

合法状态转换：
  DRAFT      → SUBMITTED     [提交]
  SUBMITTED  → APPROVED      [审批通过]
  SUBMITTED  → REJECTED      [审批驳回]
  REJECTED   → SUBMITTED     [重新提交]
  APPROVED   → ASSIGNED      [分配处理人]
  ASSIGNED   → PROCESSING    [开始处理]
  PROCESSING → RESOLVED      [提交解决方案]
  PROCESSING → ASSIGNED      [转派]
  RESOLVED   → VERIFIED      [验证通过]
  RESOLVED   → PROCESSING    [验证不通过，退回]
  VERIFIED   → CLOSED        [关闭]
  任意状态    → CANCELLED     [取消]（仅创建人/管理员）
```

## 附录D：对象存储方案评估与决策记录

### D.1 评估背景

IT运维工单管理系统的附件存储（工单附件、知识库文档、用户头像等）需要选择合适的对象存储方案。当前项目采用本地磁盘存储（`itsm.profile: D:/itsm/uploadPath`），需评估是否引入专业对象存储服务。

### D.2 候选方案

| 方案 | 类型 | 说明 |
|------|------|------|
| 阿里云OSS | 云托管对象存储 | 国内主流云存储服务，按量计费 |
| MinIO | 自建对象存储 | 开源（AGPL v3），S3兼容，Docker本地部署 |

### D.3 九维度评估对比

| 评估维度 | 阿里云OSS | MinIO | 毕业设计权重 |
|----------|-----------|-------|-------------|
| 成本结构 | ★★★★☆ | ★★★★☆ | 15% |
| 部署复杂度 | ★★★★★ | ★★★★☆ | 15% |
| 扩展性 | ★★★★★ | ★★★★☆ | 8% |
| 安全性 | ★★★★★ | ★★★★☆ | 10% |
| 性能表现 | ★★★★☆ | ★★★★★ | 10% |
| 运维难度 | ★★★★★ | ★★★★☆ | 10% |
| 技术支持与学习资源 | ★★★★★ | ★★★☆☆ | 12% |
| 系统兼容性 | ★★★★★ | ★★★★☆ | 10% |
| 应用案例参考 | ★★★★☆ | ★★★★☆ | 10% |

### D.4 决策结论

**选定方案：MinIO**

核心选择理由：

1. **离线演示保障**：答辩现场网络不稳定是真实风险，MinIO本地部署可完全离线运行，阿里云OSS断网即不可用
2. **学习价值更高**：涵盖"对象存储部署→配置→集成→运维"全链路技术能力，S3兼容API是行业标准
3. **数据自主可控**：所有数据存储在本地，不存在数据泄露到云端的风险
4. **环境一致性**：开发、测试、演示环境完全一致，避免"我电脑上能跑"的问题
5. **Docker一键部署**：部署复杂度可控，`docker run` 一行命令即可启动

### D.5 实施策略：早抽象 + 晚替换

采用"早抽象、晚替换"策略，分阶段实施：

| 阶段 | 时间 | 内容 |
|------|------|------|
| 迭代1 | 第5-6周 | 定义IStorageService接口 + LocalStorageServiceImpl（包装现有FileUploadUtils逻辑） |
| 迭代2 | 第7-8周 | 不碰存储层，专注核心业务 |
| 迭代3 | 第9-10周 | Docker部署MinIO + 开发MinioStorageServiceImpl + 配置化切换 |

核心原则：**业务代码永远只依赖IStorageService接口，不直接依赖任何存储实现**。

### D.6 存储抽象层设计

```
IStorageService（接口）
├── upload(MultipartFile, directory) → UploadResult
├── delete(fileUrl) → void
├── download(fileUrl) → InputStream
└── getAccessUrl(fileUrl) → String

LocalStorageServiceImpl          ← 迭代1实现，@ConditionalOnProperty(havingValue="local")
MinioStorageServiceImpl          ← 迭代3实现，@ConditionalOnProperty(havingValue="minio")
```

配置切换方式：
```yaml
itsm:
  storage:
    type: local    # 迭代1-2使用本地存储
    # type: minio  # 迭代3切换为MinIO
    minio:
      endpoint: http://localhost:9000
      access-key: itsmadmin
      secret-key: itsmadmin123
      bucket-name: itsm-ticket
```

### D.7 MinIO部署方案

```yaml
# docker-compose.yml
version: '3.8'
services:
  minio:
    image: minio/minio:latest
    container_name: itsm-minio
    ports:
      - "9000:9000"
      - "9001:9001"
    environment:
      MINIO_ROOT_USER: itsmadmin
      MINIO_ROOT_PASSWORD: itsmadmin123
    volumes:
      - ./minio-data:/data
    command: server /data --console-address ":9001"
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 1G
```
