## 一、V2.1 修订结论

V2.0 的问题不在于技术先进性，而在于迭代节奏不合理：在迭代2同时引入 Flowable、RabbitMQ、Elasticsearch、Prometheus、Grafana、Docker Compose，会把项目从“工单系统深化”变成“中间件集成集合”。这会带来三类风险：

1. **交付风险**：迭代2工作量从约2周膨胀到约30个工作日，压缩后续知识库、评价、统计和论文时间。
2. **兼容风险**：当前项目使用 Spring Boot 4.0.6 + Java 25，部分企业级组件的 Starter 兼容性需要验证，不能把未验证组件放到核心路径。
3. **答辩风险**：过多中间件会分散系统主题，难以清楚说明“工单流转、SLA、通知、统计”这些业务能力。

**V2.1 决策：采用“轻量核心 + 明确演进”的技术路线。**

| 能力 | 迭代内落地选型 | 不立即引入 | 后续演进条件 |
|------|----------------|------------|--------------|
| 工作流 | 自研数据库驱动流程引擎 + 当前枚举状态机校验 | Flowable | 需要 BPMN、会签、复杂网关、多租户流程时再引入 |
| 事件总线 | Spring ApplicationEvent + 异步线程池 + 通知表持久化 | RabbitMQ | 出现跨服务异步、可靠消息、死信重试需求时再引入 |
| SLA | MySQL SLA记录 + Quartz定时扫描 | RabbitMQ延迟消息 / Flowable Timer | 单机扫描性能不足或多实例部署时再升级 |
| 实时通知 | Spring WebSocket + STOMP + JWT握手认证 | 外部消息代理 | 单实例优先，多实例再补 Redis Pub/Sub 广播 |
| 全文搜索 | MySQL FULLTEXT/ngram + LIKE兜底 | Elasticsearch | 工单/知识库数据达到10万级且搜索体验成为瓶颈时再引入 |
| 可观测性 | Spring Boot Actuator + Druid + 日志 + 业务统计 | Prometheus/Grafana | 部署演示或生产化阶段作为增强项 |
| 文件存储 | 迭代1本地存储抽象，迭代3 MinIO实现 | 云OSS | 答辩离线演示优先，后续可切云对象存储 |

## 三、核心技术选型评估

### 3.1 工作流：自研数据库驱动流程引擎

迭代1已经完成 `TicketStatus`、`TicketTransition`、`TicketStateMachine`，这是非常有价值的基础，不应在迭代2直接推倒重来。迭代2应在其上增加数据库驱动能力：

| 设计点 | 方案 |
|--------|------|
| 流程定义 | `wf_workflow`、`wf_node`、`wf_transition` 定义流程、节点、边 |
| 流程实例 | `wf_instance` 记录每张工单当前流程版本和当前节点 |
| 待办任务 | `wf_task` 记录审批、分配、处理、验证任务 |
| 状态校验 | `TicketStateMachine` 保留，作为业务状态合法性校验 |
| 权限控制 | 继续使用 `@PreAuthorize` 和 RuoYi 菜单按钮权限 |
| 过程记录 | 新增 `it_ticket_process_log`，用于答辩展示完整处理轨迹 |

不立即引入 Flowable 的理由：

1. 当前流程是固定的 IT工单主流程，复杂度可控。
2. Flowable 的 BPMN、历史表、任务表、监听器模型学习成本高，会挤压业务功能时间。
3. Spring Boot 4.0.6 环境下 Flowable Starter 兼容性需要单独验证，不适合作为迭代2主路径。
4. 毕业设计答辩更看重“能解释清楚并完整演示”的流程模型，自研轻量引擎更容易说明设计思路。

后续演进策略：如果后续需要会签、复杂网关、流程模型导入导出，再将 `IWorkflowEngine` 接口增加 Flowable 实现，保留当前自研实现作为轻量模式。

### 3.2 消息与通知：Spring ApplicationEvent + 通知表

迭代2先实现应用内事件总线，不引入 RabbitMQ。

```
工单业务操作
  -> 发布 TicketEvent / SlaEvent
  -> @Async 事件监听器
       -> 写 it_notification 通知表
       -> WebSocket 在线推送
       -> 后续邮件/短信监听器复用同一事件
```

该方案的关键不是“内存事件”，而是**通知落库**：

| 风险 | 处理方式 |
|------|----------|
| WebSocket推送失败 | 通知记录已落库，用户重新登录后可拉取未读通知 |
| 应用重启导致事件丢失 | 关键动作在主事务中写业务表和过程日志，通知可通过补偿Job重扫 |
| 监听器异常影响主流程 | 使用 `@Async` + 异常日志，不阻断工单状态流转 |
| 后续改RabbitMQ | 保持事件对象和通知服务接口稳定，替换事件投递方式即可 |

RabbitMQ 暂不引入的理由：

1. 当前是单体应用，Spring Event 已能完成模块解耦。
2. 邮件、短信、WebSocket的可靠性可通过数据库通知表和补偿Job保障。
3. RabbitMQ需要交换机、队列、ACK、死信、重试、运维监控，短期复杂度高于收益。

### 3.3 SLA：Quartz定时扫描

SLA不需要一开始就使用延迟消息。迭代2采用“截止时间入库 + Quartz周期扫描”的方式：

| 表/服务 | 职责 |
|---------|------|
| `it_sla_config` | 按分类、优先级配置响应时限、解决时限、预警阈值 |
| `it_sla_record` | 记录每张工单响应/解决截止时间、状态、预警次数 |
| `SlaCalculateService` | 工单提交、分配、解决时计算 SLA |
| `SlaMonitorJob` | 每1分钟扫描即将超时和已超时记录 |
| `SlaEscalationService` | 生成预警、升级处理人或通知主管 |

该方案优点是简单、可测试、可解释。对于毕业设计和单机部署，分钟级扫描已经足够。

### 3.4 全文搜索：MySQL FULLTEXT/ngram + LIKE兜底

迭代3知识库上线后再加入全文搜索。选择 MySQL FULLTEXT/ngram 的原因：

1. 当前数据量预计较小，MySQL足够支撑工单和知识库检索。
2. 不需要额外部署 ES、IK插件、索引同步和数据一致性补偿。
3. 复杂搜索可以先通过标题、内容、分类、标签、状态等条件组合解决。

实现策略：

| 场景 | 实现方式 |
|------|----------|
| 工单列表筛选 | 继续使用索引字段 + LIKE |
| 知识库全文搜索 | MySQL FULLTEXT/ngram |
| 中文分词效果不足 | 增加关键词、标签、分类维度补强 |
| 数据量明显增长 | 抽象 `SearchService`，增加 Elasticsearch 实现 |

### 3.5 实时通知：Spring WebSocket + STOMP

WebSocket 是迭代2可以直接引入的技术，原因是它直接服务业务体验，部署成本也低。

| 设计项 | 方案 |
|--------|------|
| 连接地址 | `/ws` |
| 认证方式 | STOMP CONNECT Header 或握手参数携带 JWT |
| 订阅频道 | `/user/queue/notifications`、`/topic/ticket/{ticketId}` |
| 推送内容 | 通知ID、工单ID、标题、类型、摘要、创建时间 |
| 离线处理 | 查询 `it_notification` 未读记录 |
| 前端依赖 | `@stomp/stompjs` + `sockjs-client` |

### 3.6 可观测性：先轻量，后增强

V2.1不把 Prometheus/Grafana 放到迭代2主线。更合理的顺序是：

| 阶段 | 观测能力 |
|------|----------|
| 迭代2 | Druid SQL监控、日志、SLA/通知业务表、接口耗时日志 |
| 迭代4 | Spring Boot Actuator健康检查、关键业务指标接口 |
| 收尾/扩展 | Prometheus + Grafana 作为部署增强项 |

这样既保留技术亮点，又不会让监控系统抢占核心业务时间。

## 五、技术风险与应对

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| 自研流程引擎边界过大 | 迭代2延期 | 中 | 只实现顺序流、驳回、转派、取消；会签/复杂网关列为扩展 |
| SLA扫描延迟 | 预警不够实时 | 低 | Quartz 1分钟扫描，记录预警时间，答辩场景足够 |
| WebSocket认证复杂 | 通知联调延期 | 中 | 先实现JWT握手校验和用户频道，离线通知通过HTTP接口兜底 |
| MySQL全文搜索中文效果一般 | 搜索体验一般 | 中 | 使用标签、分类、关键词字段补强；保留ES演进接口 |
| MinIO部署影响演示 | 附件不可用 | 低 | 保留本地存储实现，通过配置一键切换 |
| 技术点过多导致论文主线发散 | 答辩表达困难 | 中 | 论文主线固定为“流程驱动的IT运维工单管理”，中间件只作为支撑 |

## 七、后续演进记录

以下技术不进入毕业设计主线，但保留为架构演进方向：

## 八、结论

当前项目最合理的技术路线不是“把企业中间件一次性全部集成”，而是围绕 ITSM 工单系统的业务闭环做深：

1. 迭代2先把**流程、SLA、实时通知、过程日志**做扎实。
2. 迭代3补齐**邮件、知识库、评论、评价、对象存储**。
3. 迭代4完成**统计仪表盘、报表、流程设计器、安全与部署文档**。

这条路线更适合毕业设计：技术点足够完整，业务闭环清晰，开发风险可控，也为后续向 Flowable/RabbitMQ/Elasticsearch 等企业级方案演进留下接口。
